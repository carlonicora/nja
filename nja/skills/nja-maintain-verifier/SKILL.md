# Maintain a verification skill

A feature map rots the moment the app changes. This is the upkeep loop for a skill generated by `nja-create-verifier` (or any project-local verification skill with a feature map).

The unit of rigor is the feature, not every sentence. Cover every feature file from source and exercise every feature live, without terminalising every bullet.

## Outcomes

- Every feature file matches what the source actually does today.
- Every feature has been driven live at least once this pass.
- Corrections land as one batch the user reviews, not as a running commentary.

## 1. Read the map

List every file under `.claude/skills/verify-<app>/features/`. That set is the work. A feature missing from the map because it was added after the last pass is also the work: diff the routes under `apps/web/src/app` and the module list against the map and add what is missing.

## 2. Source pass, in parallel

Dispatch one agent per feature file. Each one reads only its feature's source (route, components, service, controller, repository) and returns:

- Claims in the feature file that no longer match the source, each with a `file:line`.
- Selectors, routes or handles that changed.
- Sub-features that exist in source but not in the map.
- Nothing else. No fixes, no rewrites.

Give every agent the feature file plus the repo paths it needs. They do not write.

## 3. Live pass, one session

One session drives every feature through the harness the skill names — `playwright-cli` in an nja repo, loading the page twice to land logged in. Per feature, record: driven / could not reach / broken, with the evidence.

Do not fan this out. Concurrent drivers on one instance corrupt each other's state, and the ports are shared. One session, feature by feature.

Check first with `lsof -iTCP:<port> -sTCP:LISTEN` and drive whatever is already running rather than restarting it. Never kill by process name.

## 4. Reconcile

A claim is wrong only when the source pass and the live pass agree it is wrong. When they disagree, the live pass wins for behaviour and the source pass wins for structure, and you say so in the report.

Separate three buckets:

- **Map wrong.** The app changed; fix the feature file.
- **App wrong.** The map describes intended behaviour the app no longer delivers. That is a bug report, not a map edit. Do not silently rewrite the map to match a regression.
- **Both fine.** Say nothing.

The second bucket is the one that earns this pass its cost. Resist the reflex to make the document match the code.

## 5. Land one batch

At most one batch of corrections, covering the map edits only. Report the app bugs separately for the user to triage.

Do not commit. The user tests before anything reaches git.

## Cadence

Run it after a wave of feature work lands, before a release, or when a verification run starts failing for reasons that look like drift rather than defects. Do not schedule it; a pass on an app that did not change is spent tokens.
